# 第1次レビュー（v1 → v2）

初版（v1）を実測ベースで検証した結果、**そのままでは実運用に耐えない問題を6件**検出しました。
以下すべて修正し、v2として再実装・再検証済みです。

---

## 検出した問題と実測値

### 🔴 致命的1: 埋め込みが機能していなかった

v1は「ノード種別ごとのランダム初期値をK-hop伝播」していました。しかし同一種別のノードは
同じシード値から出発するため、**装置Aと装置Bがほぼ同一ベクトル**になります。結果:

| 指標 | v1 | v2 |
|---|---|---|
| 属性一致数と類似度の相関 | 0.639 | **0.982** |
| Faultペアの類似度レンジ | 0.9986〜1.0000 | **0.093〜1.000** |
| 装置A vs 装置B の類似度 | 0.9927（ほぼ同一） | 属性由来で分離 |

v1で画面に出ていた「類似度92%」は実際には全ペアが99.9%台で、**差が第4位小数にしかなく、
表示上の順位はノイズで決まっていました**。

**修正**: Fault×属性値の incidence 行列 → TF-IDF → TruncatedSVD → グラフ平滑化。
TF-IDFにより「レアな属性値ほど情報量が大きい」ことが反映され、異常検知の精度に直結します。

### 🔴 致命的2: 原因予測のラベルリーク

v1はグラフに**原因ノードを含めたまま**埋め込みを作り、その埋め込みで原因を予測していました。
過去Faultの埋め込みには正解が染み込んでいる一方、新規Faultのクエリには原因がないため、
学習時と推論時で条件が食い違う（train/serve skew）状態でした。

**修正**: 埋め込みは属性列のみから構成し、原因は検索後の集計にのみ使用。

### 🔴 致命的3: 精度検証が皆無 / 元資料の指示を未実施

元資料は「**CatBoost vs GNN を必ず比較した方がいい**」と明記していましたが、v1は
評価を一切実装していませんでした。実装して測定した結果:

| モデル | Top-1 | Top-3 |
|---|---|---|
| 多数決ベースライン | 0.298 | - |
| 埋め込みkNN（本アプリ①） | 0.488 | 0.802 |
| **勾配ブースティング（CatBoost相当）** | **0.496** | **0.835** |

**資料の警告どおり、表形式モデルが埋め込みkNNを上回りました。**
→ 原因予測は表形式モデルを本番採用し、グラフ/埋め込みは②パターン発見・③類似検索に使うのが合理的です。
v2はこの比較表をUIに常設し、判断できるようにしました。

### 🔴 致命的4: 大規模データでクラッシュ

| 件数 | v1 パターン発見 | v2 パターン発見 |
|---|---|---|
| 5,000 | 98.9秒 | **2.0秒**（50倍） |
| 20,000 | **OOMで強制終了** | **4.8秒** |
| 100,000 | 測定不能 | **23秒** |

原因は3つ:
1. `S = X @ Xᵀ`（Fault間類似度）を実体化 → 5,000件で既に77%密、20,000件でメモリ枯渇。
   → 結合則 `S E = X (Xᵀ E)` に書き換え、n×n行列を作らず **O(nnz·d)** に。
2. コミュニティ検出をFaultノード込みの巨大グラフ上で実行（91秒）。
   → 属性ノードのみの小グラフ（最大80ノード）上で実行。表示内容は同じで一瞬。
3. 共起集計がPythonの二重ループ（96秒）→ 疎行列積 `Bᵀ B` で一括計算。

加えて評価関数が10万件で15.6GiB要求 → チャンク処理化、シルエット係数もサブサンプル化。

### 🟠 セキュリティ: 保存型XSS

CSVの値をエスケープせず `innerHTML` に投入していた箇所が**10箇所**。
`<img src=x onerror=alert(1)>` を含むCSVをアップロードすると任意JSが実行されます。

**修正**: `esc()` を実装し全描画経路に適用（36箇所）。ペイロード無害化を実地テストで確認済み。

その他: `secret_key` のハードコード、`debug=True`、アップロードサイズ無制限、
セッションストアが無制限に増え続けるメモリリーク → すべて修正（環境変数化 / LRU+TTL / サイズ上限）。

### 🟠 要件の取りこぼし: 時系列

元資料は「装置B × E205 × 夜勤 × 高湿度が**最近急増している**」を発見したい例として挙げていましたが、
v1は時間軸を一切持たず、「急増」を検出する手段がありませんでした。

**修正**: 日付列があれば直近N日 vs それ以前で構成比を比較し、リフト値で急増パターンを検出。
検証用にサンプルデータへ日付を付与したところ、仕込んだパターンを正しく検出しました:

```
部品×Error: Sensor × E205 :  0.00% →  8.62%  (新規出現)
Error×条件: E205 × 夜間    :  0.35% →  8.62%  (×24.7)
症状×Error: 発熱 × E205    :  0.70% → 11.21%  (×16.0)
```

### 🟡 堅牢性

- ID列など高カーディナリティ列がグラフを爆発させる → 自動除外（ただし小規模データで
  全列が誤除外されるバグを検証中に発見し修正済み）
- クラスタ数が `n//15` の恣意的なヒューリスティック → シルエット係数で自動選択
- クラスタの特徴が単なる最頻値 → **リフト値**（全体平均比）に変更。
  「そのクラスタ固有の特徴」が分かるようになります
- 文字コード自動判定（UTF-8 / CP932 / UTF-16）、例外のトレースバック秘匿

# 第2次レビュー（v2 → 現行）

v2 を再検証したところ、**設計上の欠陥5件・運用上の欠陥5件**が残っていました。すべて修正済みです。
実行方法・残る限界は README を参照してください。

## 🔴 1. v1が「使うな」と書かれたまま同梱され、しかも起動不能だった

`app.py`（v1）は `templates/index.html` を返しますが、その index.html が読み込むのは
`static/app2.js`（v2用）でした。**v1は起動しても動きません**（v2にしかない `/api/evaluate` を叩き、
レスポンス形式も食い違う）。にもかかわらず、v1には既知の保存型XSS・`debug=True`・
`host=0.0.0.0`・secret_key ハードコードが残ったままでした。

動かない上に危険な参照実装を配布物に含める理由がないため、v1（`app.py` / `graph_engine.py` /
`static/app.js`）を削除し、v2を正式名称（`app.py` / `graph_engine.py` / `static/app.js`）に統一しました。
比較したい場合は git 履歴から参照できます。

## 🔴 2. 「急増パターン」に統計的裏付けがなかった

v2の判定は構成比の比（リフト値）だけでした。直近3件しかない組合せでも
`0.35% → 8.62% ＝ ×24.7` のように大きな倍率が出るため、**偶然のゆらぎと本物の急増が区別できません**。

修正: 帰無仮説「直近の発生率は以前と同じ」の下でのポアソン上側確率を p値として計算し、
Benjamini-Hochberg 法でFDR補正した q値を併記、`significant` フラグで「有意」「参考」を分けました。
併せて単一属性の急増も検出対象に加え、欠損値の組合せを除外しました（下記4）。

検証: 相関を仕込んでいない一様ランダムなデータ400件では**有意判定が0件**になること、
サンプルデータでは仕込んだ 装置B×E205×夜間/高湿度 が有意判定されることをテストで固定しました。

## 🔴 3. 欠損値が「nan」という属性値として扱われていた

`astype(str)` で `NaN` が文字列 `"nan"` に化け、急増検知のパターン名に `nan × E205` のような
実在しない組合せが出ていました。属性列を読み込み時に正規化（欠損・空文字・空白のみ → NaN に統一、
前後空白を除去）することで解消。`" 装置A"` と `"装置A"` が別の属性値に分裂する問題も同時に解決します。

## 🔴 4. クエリ埋め込みだけ平滑化されていなかった（train/serve skew）

保存済みFaultの埋め込みは近傍平滑化を通っているのに、`embed_query()` は平滑化前の空間に
ベクトルを作っていました。**既存Faultとまったく同じ属性を入力しても類似度が1.0になりません。**

| | 修正前 | 修正後 |
|---|---|---|
| 既存Faultと同一属性を入力したときの自己類似度（平均） | 0.9922 | **1.0000** |

各ホップの中間表現を保持し、クエリにも同じ演算を適用することで解消しました。

## 🔴 5. APIパラメータが無検証だった

`n_clusters` は `min(値, n-1)` で丸めるだけだったため、`{"n_clusters": 199999}` を投げると
20万クラスタのKMeansが走ります（事実上のDoS）。`contamination: 0.9` は sklearn の
`InvalidParameterError` をそのまま英語で返していました。

修正: サーバ側・エンジン側の両方で全パラメータを範囲検証（クラスタ数 ≤ 30、contamination ∈ [0.005, 0.5]、
recent_days ≤ 3650、top_k ≤ 100）。数値でない値は 500 ではなく 400 と日本語メッセージで返します。

## 🟠 6. 性能: 行単位ループとクラスタリングの二重学習

| 処理 | 20,000件 | | 100,000件 | |
|---|---|---|---|---|
| | v2 | 現行 | v2 | 現行 |
| 構築 | 1.40秒 | **0.57秒** | 6.18秒 | **2.09秒** |
| パターン発見 | 13.97秒 | **3.99秒** | 25.07秒 | **7.22秒** |
| 精度検証 | 1.20秒 | 1.17秒 | 11.82秒 | **1.36秒** |

原因と対処:
1. 共起集計が `df.iterrows()` と `df.iat` の行単位ループ（20,000件で1.7秒、うち8割が `iat`）。
   しかも `itertuples()` の結果を使わず捨てる残骸コードがありました → 列単位の `pd.factorize` に置換。
2. クラスタ数探索が全件でk=2..10を試したうえ、確定後にもう一度全件で学習し直していた（20,000件で11.4秒）
   → 探索はサブサンプル上で行い、確定した k のみ全件で1回学習。
3. クラスタ特徴のリフト計算が、クラスタごとに全体分布を再計算していた → 一度だけ計算してキャッシュ。
4. 共起グラフの構築が全非ゼロ要素をPythonで走査していた → 疎行列スライスで上位ノードのみ抽出。
5. 精度検証は行数上限（3万件）を設けたうえ、kNN投票をベクトル化。

## 🟠 7. Fault ID の全件をブラウザに渡していた

`/api/fault_ids` が全Fault IDを返し、フロントが `<select>` に全件展開していました。
上限の20万件では確実にブラウザが固まります → サーバ側検索＋件数上限（既定200件）に変更し、
UIも `datalist` によるインクリメンタル検索にしました。

## 🟠 8. CDNに1つでも到達できないと解析結果が全部消えていた

Bootstrap / FontAwesome / vis-network をCDNから読み込んでいるため、閉域網では
`vis is not defined` で描画処理が例外終了し、**その前に描画済みだった急増パターン・クラスタ・
異常検知の結果まで、まとめてエラー表示に置き換わっていました**（実機のブラウザで再現確認）。

修正: セクションごとに描画を分離して例外を局所化し、vis-network 不在時はネットワーク図だけを
代替メッセージにしました。CDN未到達時は画面上部で通知します。

## 🟠 9. その他の運用・セキュリティ

- **CSRF対策なし** → POST系APIに `X-CSRF-Token` を要求。
- **CSPなし** → `script-src` を自ホストとcdnjsに限定（`esc()` が破られた場合の二重の防御）。
- **アップロードの例外メッセージをそのまま返却** → 内部情報を出さない定型文に変更。
  文字コード判定も、デコード失敗だけでなくパース失敗でも次の候補を試すよう修正。
- `api_guard` が `functools.wraps` を使っておらず、同名関数のルートが衝突しうる状態 → 修正。
- `JSON_SORT_KEYS` は Flask 3 では無効な設定で、属性入力フォームの並びが**列順ではなく辞書順**に
  なっていた（実機のブラウザ確認で発見） → `app.json.sort_keys = False` に修正。
- 勾配ブースティングの `OrdinalEncoder` を**全件で学習**していた（検証分のカテゴリ語彙が学習側に漏れる）
  → 学習分のみで学習し、未知カテゴリは欠損として扱うよう修正。
- コミュニティの `n_faults` は実際には属性値の出現回数の合計で、Fault件数ではなかった → `n_occurrences` に改名。
  そもそもUIに表示されておらず、READMEの「関連コミュニティが表示されます」が嘘になっていた → 表示を追加。
- 解析結果キャッシュがロックなしで共有されていた → `threading.RLock` で保護。

## 🟡 10. テストが1件も存在しなかった

v2は「実測で検証した」と書かれていましたが、検証コードは配布物に含まれていませんでした。
そのため上記の不具合はすべて再発を検知できない状態でした。

**pytest 54件**（エンジンの回帰テスト + HTTP APIのテスト）と `benchmark.py` を追加し、
本レポートの主張を再現可能にしました。

```bash
pip install -r requirements-dev.txt && pytest
```
